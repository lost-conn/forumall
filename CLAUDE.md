# CLAUDE.md — Forumall

Forumall is a reference implementation of **OFSCP** (Open Federated Social Communications Protocol) — a single Bun monorepo that is **both an OFSCP provider (server) and its web client**, designed to be **trivially self-hostable** (one process, one port, one SQLite file). Status: **OFSCP v0.1 feature-complete and conformance-tested** (P0–P10 delivered; the WebRTC Calls epic §9 is deliberately deferred — see the Forumall board BACKLOG).

The protocol spec is the **single source of truth** and lives in the sibling repo **`../ofscp`** (`docs/ofscp_spec.md`, `schemas/v0.1/**`, conformance fixtures in `tests/`). Section refs like "§4.4.2" point there. **Treat `../ofscp` as read-only** from this repo; if you find a spec/schema inconsistency, report it and PR it against `lost-conn/ofscp` (4 such PRs already filed) — do not silently work around it.

## Monorepo layout
```
packages/shared/   OFSCP protocol primitives — signing, dmId, Zod schemas. Imported by BOTH server and web (the keystone).
packages/server/   Hono provider: HTTP + WebSocket, bun:sqlite + Drizzle. Also serves packages/web/dist as static (one process).
packages/web/      SolidJS + Vite + UnoCSS client. Consumes @forumall/shared.
e2e/               Playwright end-to-end (single- and two-provider). Boots the real server + built web bundle.
```
Workspace package names are `@forumall/{shared,server,web,e2e}`.

## Stack
Bun · Hono · bun:sqlite + Drizzle · Zod · `@noble/ed25519`/`@noble/hashes` · Argon2id (`@noble/hashes/argon2`) · SolidJS + Vite + UnoCSS + `@solidjs/router` + `@tanstack/solid-query` · Biome (lint/format) · Playwright. **All deps are pure-JS (no native build step)** — a self-host requirement; keep it that way.

## Commands (run from repo root)
- `bun install`
- `bun run typecheck` — per-package `tsc --noEmit` across all four packages, test code included (every package's tsconfig includes `test/**`). Under `noUncheckedIndexedAccess`, index test arrays with `at(xs, i)` (`packages/server/test/helpers/at.ts`) rather than a cast.
- `bun run test` — **scoped** unit/integration via `--filter` (shared + web + server). **Use this, NOT bare `bun test`** — bare `bun test` scans into `e2e/` and pulls Playwright `*.spec.ts` into Bun's runner, producing ~7 spurious "did not expect test()" errors. Per-package: `bun test packages/server`.
- `bun run build` — vite build of the web bundle → `packages/web/dist`.
- `bunx biome check .` (or `bunx biome check --write .` to fix). Keep it clean; CI runs it.
- `bun run test:e2e` — Playwright (the fixture builds the web bundle first). `bun run test:all` = unit + e2e.
- Boot the server: `bun run packages/server/src/index.ts` (zero-config localhost boot works; set `DOMAIN` for a real deploy).

**Every authenticated change should end green on:** `bun run test` + `bun run typecheck` + `bunx biome check`. The server suite uses `app.request(...)` (HTTP) and real `Bun.serve` + `new WebSocket` (WS) — no mocks.

## `packages/server` — the provider
Conventions (follow them when adding features):
- **Add a table:** define it in `db/tables/<domain>.ts` (re-exported by the `db/schema.ts` barrel), write the migration as a named constant in `db/migrations/<domain>.ts` and append it to the `migrations` list in `db/migrate.ts` (forward-only, applied on boot; currently through `0042`). Greenfield — no back-compat needed.
- **Add a router:** create `http/<feature>.ts`, mount it in `http/api.ts` (under `/api`) or in `app.ts` for root paths (`/.well-known/*`, `/invite/*`, static).
- **Auth a route:** `requireSignature()` (must be authed → sets `c.var.actor = {actor,handle,keyId,domain}`), `optionalSignature()` (no `X-OFSCP-*` header → anonymous; any → §4.5 — for every route that serves unsigned callers: the §4.5 anonymous-reader routes (group/channel/history/replies GETs and `/api/users/{userRef}/{profile,presence,groups}`; NOT `…/members`, which is `requireSignature()`) and every public route that needs no caller (discovery, keys endpoint, `/api/health`, `/api/tiers`, `/problems/*`, `GET /api/provider`, media GET, register/login/device-key registration, guest creation…), so the §8 inbound policy gives a signed request from a denied peer `403`; **every new public route must mount it**), `requireProviderSignature()` (§8.1; no production route — the spec defines none), or `requireActorOrProviderSignature()` (only the `/api/federation/dms` edit/delete/reaction ingest, for Forumall's provider-signed DM forwarding, a spec deviation slated for removal in audit unit U23). **The request's headers name the signer kind, the route names the kinds it accepts:** user signatures by default (every route of the spec). All in `http/signature.ts`, which implements the **ordered §4.5 checks**: step 1 (all six headers, exactly one of `X-OFSCP-Actor`/`X-OFSCP-Provider` — both → `401`, never the deny `403`) → authority → ±300s skew → nonce replay → body digest → §8 deny `403` → `401` for a signer kind the route does not take (no discovery fetch, no verification, no nonce, never an anonymous viewer) → replay-store warm-up `503` → key resolution → Ed25519 verify → record the nonce. Order is security-critical, don't reorder. Step 6 key resolution lives in `http/signer-resolution.ts`.
- **Errors:** throw `AppError.{badRequest,unauthorized,forbidden,notFound,conflict,...}` from `http/errors.ts`; the central handler (`createProblemHandlers`, bound in `app.ts`) renders RFC 7807 `application/problem+json`. Every problem carries a §7.3 registry `errorCode` (`ERROR_CODE_REGISTRY`: each code has a fixed status) and `type` = `https://{canonicalAuthority(config.domain)}/problems/{errorCode}` (§2.6) — never a shared base; `GET /problems/{errorCode}` serves the description (`http/problems.ts`). WS `error` events use the same registry: `errorEvent(code, message, correlationId?)` in `http/ws/connection.ts` derives `status` from the code.
- **Authorize:** the permission resolver is `provider/permissions.ts` — `can(action, role, group)` / `canActor(db, action, groupId, actor)` / `getMembership` / `grantsOf` / `roleHoldsAll`. **Exact membership (§5.2):** an action is allowed iff the actor's role is listed verbatim in `group.permissions[action]` — *no rank inheritance*; `owner` is the implicit super-role (always allowed). Powers need not be nested. A group declares custom roles via its `roles` catalogue (`RoleDefinition[]`); a role's grant set is derived from the permission map, not the catalogue. Kick/role-change obey the **subset (self-protect) rule** `roleHoldsAll` — a caller may act on a target only if it holds every permission the target holds (owner protected). Channel read access (§11.3) is `canViewChannel` (`provider/channels.ts`; `roleListed` is the exact-membership test). **Hidden channels answer as missing:** every request naming a channel resolves it with `getReadableChannel` — REST via `requireReadableChannel`, WS/mutation helpers via `CHANNEL_NOT_FOUND` (`http/channel-access.ts`) — so an unreadable channel gets exactly the missing-channel `404`/`not_found`, *before* any permission check; `403` is only for a reader lacking a permission (`manage`, `post:<type>`, `react`). Exceptions: the channel-join alias (answers as a group join) and `GET …/channels` / `GET /api/groups/{id}` for an unreadable group (still `403`; open spec question). **Reading never implies participating (§11):** reacting needs membership + `canReact` (channel `react` override, else any member); `typing.start` needs a `post:<type>` grant for some type (§7.1; `memberChannelContext` in `http/message-mutations.ts` builds the authz context for all three); withdrawing a reaction needs read access only.
- **Real-time:** the connection hub is `provider/ws-hub.ts` — `hub.publishToChannel(channelId, event)` and `hub.publishToActor(actor, event)`. It's on `c.var.hub`. **REST mutations must also fan out over the hub** so WS subscribers see them (e.g. REST message edit/delete publishes `message.updated`/`deleted`). **The requester's own copy (§7.1):** a WS command passes `reply = { conn, correlationId }` to `publishToChannel`, which writes that connection exactly one correlated copy whether or not it is subscribed, and the uncorrelated event to every other subscriber. **Only changes fan out:** a repeated delete of a tombstone (`deleteChannelMessage`, `http/message-delete.ts`), a repeated reaction add and a remove that removes nothing (`addChannelReaction`/`removeChannelReaction`, `http/reaction-mutations.ts` — shared by WS and REST) fan out nothing; REST answers as usual (`204`, the existing `Reaction` with `200`), WS sends the correlated event to the requester alone (a repeated delete's `message.deleted` has no `cursor`). An edit of, or reaction add to, a tombstone is `404`. **Typing** is the actor's across connections (`http/ws/channel-typing.ts`, `WsCtx.channelTyping`): a stop from any connection ends it, a stop with no active start sends nothing, and expiry/disconnect of one connection emits `stop` only if no other still types. Resume replays a since-deleted message as `message.created` (tombstone) then `message.deleted`, same cursor. `http/ws.ts` owns the connection lifecycle and dispatches each command (`COMMANDS` table) to its module under `http/ws/` (`authenticate`, `subscriptions`, `messages`, `reactions`, `typing`, `presence`); handlers take a `WsCtx` (`http/ws/connection.ts`).
- **Message create (§7.1):** WS `message.create` and REST `POST …/channels/{channelId}/messages` both call `createChannelMessage` (`http/message-create.ts`), which runs the spec's ordered checks (key parse → 404 visibility → 403 `post:<type>`/reply-only → duplicate lookup → full-body 400 + reply target → `replyOnlyTo` 403), stores and fans out, then derives notifications (`provider/message-notifications.ts`: a stored `mentions` list is exactly who is mentioned, `[]` nobody; only without it is the text parsed, §10.1). Edits never notify. Authorization helpers live in `http/message-mutations.ts` (`authorizePostAccess`, `authorizeReplyTarget`). DM routes: `http/dms.ts` (the map + history reads), `http/dm-conversation-routes.ts` (`/me/dms` list + pointer PUT), `http/dm-reaction-routes.ts`, `http/dm-edit-routes.ts`, `http/dms-federation.ts` (`/federation/dms`), with `dm-events.ts` (fan-out) / `dm-request.ts` / `dm-forwarding.ts` helpers.
- **WS transport rules (§7.1, lost-conn/ofscp#27):** `http/ws.ts` routes frames through `http/ws/dispatch.ts` (`decodeFrame`, `routeCommand`). Before `authenticated`, anything but `authenticate` closes `4001`; a failed or malformed `authenticate` sends an `error` mirroring REST (`401`; `403` policy; `503` + `details.retryAfter` for an unfetchable remote key, `remoteLookupFailure`) then `4001`. After it: no `id` → uncorrelated `bad_request`; bad `data` or a standard command with no handler → correlated `bad_request`; unknown non-standard types are ignored; command `ts` is ignored. `4001`/`4003` only for the spec table's reasons: idle `1000`, shutdown `1001` (`app.__closeWebSockets`, SIGTERM in `index.ts`), oversized frame `1009` (Bun `maxPayloadLength` = `WS_MAX_FRAME_BYTES`), connection cap `too_many_requests` + `1013` (`WS_MAX_CONNECTIONS_PER_ACTOR`, in place of `authenticated`). `subscribe` acks the readable channels, then one `not_found` with `details.channels` for the rest; the `WS_MAX_SUBSCRIPTIONS` cap is all-or-nothing over readable channels. `presence.subscribe` does the same with `details.users`. Tests share `test/helpers/ws-harness.ts`.
- **Loss of access (#15):** a REST mutation that can *reduce* channel read access (membership removal, role change, channel tier/`permissions`, deletion) MUST call `revalidateGroupSubscriptions`/`revalidateChannelSubscriptions` (`provider/access-revocation.ts`) after committing — it re-runs `canViewChannel` for live subscribers and sends an unprompted `unsubscribed {channels, reason:"access_revoked"}`. Revoking a device key (or re-binding it, guest claim/merge) calls `terminateKeySessions`/`terminateHandleSessions` → close `4003`. `app.ts` also installs a delivery-time gate on the hub (non-public channels) as defence in depth. `reason` and `4003` are specified in OFSCP §7.1 ("Losing access", "Close codes") — lost-conn/ofscp#11. A **remote** actor's direct-WS key follows §7.1 as of lost-conn/ofscp#22 (`http/ws/remote-key-watch.ts`): `4003` only when a completed fetch shows the key gone (`no_key`, or a different public key under the id); `4001` when the cache entry vouching for it (`KeyLookup` `found.expiresAt`) lapses with no completed re-fetch — failed, rate-limited, refused or never tried — or at the first failed re-fetch when nothing was cached, and at once when the peer becomes federation-denied. Every check first consults `userKeysCache.lastCompletedFetch(actor, keyId)`, so a fetch made by a REST verify or another connection also ends (key gone → `4003`) or extends the confirmation. Re-fetches are forced from a refresh point (`remoteKeyRefreshLeadMs` before expiry, or halfway through a shorter entry); the watch's own timer wakes at that point, at halving retry points, and at expiry, so none of this waits for a heartbeat. Expiry is on the cache's clock (`userKeysCache.now()`). A handshake whose socket closed during the remote key fetch is never registered (`ConnState.closed`).
- **Provider helpers** (`provider/*.ts`) hold the storage + domain logic, kept separate from HTTP: `signing-key.ts` (`getProviderSigningKey`), `password.ts` (Argon2id), `bootstrap-token.ts`, `device-keys.ts` (`resolveActorKeys`, `revokeDeviceKey`), `nonce-store.ts`, `messages.ts` (`createMessage`/`listMessages` + the global monotonic `seq` cursor), `reactions.ts`, `dms.ts`, `membership.ts` (the reusable opaque-cursor codec `encodeCursor`/`decodeCursor`), `invites.ts`, `guests.ts` (`buildUserProfile`), `contacts.ts` (`areContacts`), `privacy.ts` (`getPrivacySettings`), `visibility.ts` (`canView`), `presence.ts`, `follows.ts`, `media.ts` + `storage.ts`, `notifications.ts`, `known-providers.ts`, `discover.ts`, and `federation/*`.
- Config: `config.ts` — env-driven with defaults (`PORT`, `DOMAIN`, `DATA_DIR`, `MEDIA_DIR`, `DB_PATH`, Argon2 params, `MAX_UPLOAD_BYTES`, token/cache/timing windows, edit windows (`MESSAGE_EDIT_WINDOW_SECONDS` for chat types and DMs; `ARTICLE_EDIT_WINDOW_SECONDS`, unset = articles have no `editUntil` and no time limit, and a set value below the chat window is rejected at boot — `provider/edit-window.ts`, `messages.edit_until` NULL), `ENABLE_KNOWN_PROVIDERS`/`ENABLE_DISCOVER_FEED`, `FEDERATION_ALLOW`/`DENY`, `FEDERATION_INSECURE_LOCALHOST`). Boots with only `DOMAIN` (or nothing locally). See `.env.example`.

## `packages/web` — the client
- `lib/ofscp-client.ts` — signing HTTP client `{baseUrl, authority, actor, keyId, privateKey}` → signed `get/post/patch/delete` + bootstrap/device-key plumbing. **Use `postBinary` for binary bodies** (the JSON path UTF-8-decodes and corrupts binary, e.g. media uploads).
- `lib/ofscp-ws.ts` — WS client (signed-challenge handshake, subscribe registry, ping/pong, auto-reconnect + `since` resume) + `OfscpWsRegistry` (one client per provider host — home + foreign). **Send every command with `ws.send(type, data, opts)`**, never a raw frame: nothing but `authenticate` is written before `authenticated` (§7.1 closes `4001`). Until then commands wait in an ordered outbox flushed after the resubscribe; `whenDisconnected: "drop"` (typing, fresh presence subscribes) skips the queue instead; `idempotent: true` (`message.create` with a `clientMessageId`) is re-sent under the same frame id when the socket drops before its answer; a terminal close (`close()`, `4003`, no auto-reconnect) calls each queued command's `onUndelivered`.
- `lib/registration.ts` — §4.1.1 registration mode (`ProviderInfo.registration` from discovery; unknown → `open`), the `registration_closed`/`invite_required` messages (read from the problem `errorCode`), and `/register?invite=` links. Register and guest claim send an optional `inviteToken`; `invite_required` after sending one retries as a login (the token may be spent by a lost earlier success).
- Uploads (§5.8): `uploadMedia(client, file, { target })` adds a `target` part (canonical authority of the provider that will hold the message: the channel's home, a DM's recipient provider). Composers keep `PendingUpload`s (`lib/pending-uploads.ts`, via `useComposerUpload(target)` in `components/shared/composer.ts`) and `attachmentsForSend()` re-uploads any made for another target before sending.
- Mentions: `lib/mentions.ts` `mentionedActors(text, hostingAuthority)` gives the canonical `mentions` for channel messages (hosting = channel's provider) and DMs (the recipient's provider); its `MENTION_RE` follows §10.1 and matches the server's notification parser.
- `lib/federation.ts` — `clientForHost`/`domainOf`/`isLocalActor` for cross-provider calls.
- `lib/key-store.ts` — device private key in IndexedDB (in-memory fallback).
- `stores/*` — Solid `createStore`/`createSignal` module stores (session, chat, dms, presence, feed) + `auth-controller`/`presence-controller`.
- `components/{groups,chat,dms,social,feed}/*`, `routes/pages.tsx`, `App.tsx`. Composers are `chat/ChatComposer.tsx` and `dms/DmComposer.tsx`; DM logic is split into `dms/dm-controller.ts` (open/history), `dm-send.ts`, `dm-mutations.ts` (reactions/edit/delete), `dm-typing.ts`, `dm-delivery.ts`, `dm-errors.ts`. UnoCSS tokens/shortcuts in `uno.config.ts`.

## Load-bearing invariants & gotchas (read before touching these areas)
- **Signing authority ≠ transport host.** The server reconstructs the canonical string using its own `config.domain` as the authority, never the request `Host`. The web client must therefore set `authority` (HTTP) / `host` (WS) to the **provider's logical domain**, not the transport URL. The e2e harness pins `DOMAIN=localhost:<port>` so `location.host` matches. This is the whole foundation of authority-binding (§4.4.2) and federation.
- **`message.created` / `message.updated` / `dm.message` carry the full `Message`** (ofscp#23), which echoes `clientMessageId` to everyone when the create had one (history and resume replays too). Optimistic-echo reconciliation still correlates on the **`correlationId`** the author's own copy echoes (= the `message.create` command frame id, §7.1); the chat controller keeps a `frameId → clientMessageId` map. A duplicate-create answer is sent only to the requester and has **no `cursor`**: the controller treats it as the pending send's result (no new message, cursor unchanged), and `retrySend` re-sends a failed echo under its original `clientMessageId`.
- **WS subscribe must precede the async history backfill.** The hub fans `message.created` only to *current* subscribers; register listeners + `subscribe` synchronously before awaiting history, or a fast send races ahead and the author's echo never arrives.
- **Cursor space is unified.** REST history paging and WS resume (`since`) share one global monotonic `seq` (`encodeMessageCursor`). Edits/deletes keep their original `seq` (tombstones too); resume replays messages with `seq > since` in current state (edits to messages *before* the cursor are reconciled via REST, per §7.1/§8.5).
- **DM recipient resolution is O(n) over local users** (`deriveDmId(author, u@domain) === dmId`); a non-match → 400 (inbox-poisoning guard, §8.3). DMs are stored **only in the recipient's inbox** (no sender copy); the client retains its own sent messages locally.
- **DM real-time = implicit + `dmId` subscriptions (§7.4).** `publishDmMessage` / `fanOutDmReaction` (`http/dm-events.ts`) go through `hub.publishToAudience`: implicitly to the inbox owner (reactions: every LOCAL participant) plus the connections subscribed to the `dmId` whose actor is the message's author — one frame per connection. A remote actor gets DM events only through its `dmId` subscription (direct-WS, §8.5). Subscribing (`http/ws/dm-subscriptions.ts` `mayFollowDm`) needs `dmId = derive(actor, some local user)` or, for a local actor, a consistent conversation row; `since` replays the subscriber's `GET /api/dms/{dmId}/messages` rows after the cursor. `dm.typing` follows the same participant rule and reaches a remote counterparty through its subscription. A non-participant gets exactly the unknown-`dmId` answer on every DM path (§7.4 "Non-participants answer as unknown"): 404 over REST, the §8.3 edit/delete/reaction ingest included; `not_found` for WS subscribe and typing; read markers ignore it. Only the send's own `{dmId}` 400 is exempt — tested in `dm-subscriptions.test.ts`.
- **Presence/visibility filtering is per-(subject,viewer).** `canView` precedence: self → denyList → allowList → policy (`public`/`authenticated`/`sharedGroups`/`contacts`/`nobody`). Unauthorized viewers get a uniform `offline`. WS fan-out and `GET .../presence` MUST agree for the same viewer. Note: the server does not re-fan presence on a contact-accept tier crossing — the client refreshes/reloads.
- **Replay-store warm-up (§4.5 "Restarts").** The nonce store is in-memory, so until T₀ + skew (T₀ = store construction; 300s on the provider's clock, longer for a client whose clock lags) every signature timestamped before T₀ + skew that would go on to be verified gets **503** `service_unavailable` + `Retry-After` (the WS `authenticate` handshake is exempt; a request failing §4.5 steps 1–5, a denied signer's `403` and a not-accepted signer kind's `401` keep their answers, as they record no nonce). Test harnesses that sign right after boot pass the **test-only** `createApp` dep `testOnlySkipReplayWarmup: true` (all server/web suites, `test/helpers/two-provider.ts`, `e2e/harness/boot-server.ts`); `src/index.ts` never does and it is deliberately not an env/config knob. Tests for the warm-up itself inject `new InMemoryNonceStore({ now })` (skew, warm-up and expiry all use the store's clock). **Retry policy:** a 503 + `Retry-After` is retried by RE-SIGNING (fresh timestamp + nonce) only for idempotent requests and only for a usable `Retry-After` (shared strict `parseRetryAfterMs`: positive delta-seconds or future IMF-fixdate, ≥1s; 0/past/malformed → no retry) — server `signedProviderFetch({ retry })` (`BACKGROUND_RETRY` ≤ 2×skew + 60s = 660s, 6 attempts, for notification delivery — a lagging sender can be told to wait up to ~2×skew; `INLINE_RETRY` ≤10s for DM forwards made while the user's request waits, whose 503 + `Retry-After` is then relayed), web `OfscpClient.request` (GET/HEAD/PUT/DELETE, or POST/PATCH with `{ idempotent: true }` such as DM send with `clientMessageId`; ≤15s, then an `OfscpHttpError` with a user-facing message + `retryAfterSeconds`).
- **Single-process assumptions** (fine for the self-host single-node target): in-memory nonce store, in-memory hub, `seq = MAX(seq)+1`. A multi-process deployment would need shared stores / a real sequence (interfaces are pluggable).
- **CORS is required for browser federation.** `http/cors.ts` is wildcard + **credential-less** on purpose: the Ed25519 signature is the credential, the server never trusts `Origin`/`Host`, and there are no cookies. A preflight is exactly §3.4's (`OPTIONS` + `Origin` + `Access-Control-Request-Method`, → 204); other responses to a request with `Origin` get ACAO `*`, the expose list, and `Origin` *added* to `Vary`. The WS upgrade is never Origin-checked. Tests: `test/cors.test.ts`.
- **Attachments are capability URLs served from the web client's own origin** (`GET /api/media/{id}`, unsigned; no listing route). So `http/media-headers.ts` hardens every response (§5.8): `Content-Disposition: attachment` for all but non-SVG `image/*`, `video/*`, `audio/*` (RFC 6266/8187 filename), `Content-Security-Policy: sandbox` and `nosniff` always, and **never publicly cacheable** (`private, max-age, immutable`; the uploader can't know every referencing message is public) with the stored `sha-256` hash as a strong `ETag` → `304` (`http/conditional.ts`). Tests: `test/media-serving.test.ts`.
- **`FEDERATION_INSECURE_LOCALHOST` is dev/test only** (default off): rewrites `https://localhost:<port>` peer fetches to `http`. Production is https-only.

## Federation (P7)
Remote actors verify because the signature middleware resolves their keys from their home provider's `/.well-known/ofscp/users/{handle}/keys` (`federation/user-keys-cache.ts`) and remote provider keys from discovery (`federation/discovery-cache.ts`); both cache + re-fetch on a verify miss (§4.6/§8.1). They report a `KeyLookup` outcome (`federation/key-lookup.ts`) and `http/signer-resolution.ts` maps it: no matching key → 401, outbound rules refuse the fetch → 401, keys could not be fetched (DNS failure/timeout, non-200, invalid or mismatched document) → **503** + `Retry-After`. Only an **unexpired** cache entry counts — never fall back to an expired one after a failed fetch. **Fetches are bounded per identity** (actor / provider authority; `federation/refetch-limiter.ts`, §4.6 + §8 "Outbound requests"): concurrent lookups share one in-flight fetch, and at most one fetch starts per `refetchIntervalMs` (cache option, default 1 s). The identity is the requester's choice, so for **user keys** that alone does not protect a third party (`r1@victim`, `r2@victim`, … are all new actors): every new user-key fetch is also admitted **per host contacted** (canonical authority; `federation/host-fetch-limiter.ts`): a token bucket (default burst 20, then 5/s) plus at most 4 in flight, set via the `hostFetchLimits` cache option; per-host state is swept once idle for a full refill and LRU-capped (`maxHosts`, 10 000). Discovery needs no second limit: its identity already is the host. It bounds load per host, not total egress. **Cache memory is bounded too** (identities are requester-chosen): both caches keep documents in `federation/expiring-entries.ts` `ExpiringEntries` (expired entries removed, at most `maxCachedDocuments` — default 10 000 — least recently used evicted; an evicted entry just means a re-fetch), a key document body is read only up to `maxDocumentBytes` (default 64 KiB, `Content-Length` or streamed; larger → `fetch_failed`), and the user-keys cache's last-fetch record is capped by `maxRememberedFetches`. Count options throw `RangeError` unless an integer ≥ 1. A lookup whose fetch either limit suppresses (and with no unexpired cached key) is `rate_limited` → **503** + `Retry-After` = the wait rounded up to whole seconds (≥ 1; for a full in-flight cap, until the oldest fetch's egress deadline); WS re-resolution treats it like a fetch failure (session kept). Two-provider tests step past the interval with `fed.advanceCacheClock(ms)`, not sleeps. **Egress** (`federation/egress-guard.ts`): `guardedFetch` has ONE deadline (`DEFAULT_EGRESS_TIMEOUT_MS`, 5 s) covering DNS + request + body, so an inbound request never waits past a proxy's ~10 s window; a non-public address is `EgressBlockedError` (policy), an unresolvable name is `EgressResolutionError` (transient). `federation/policy.ts` `isProviderAllowed` (allow/deny, deny wins) short-circuits **before** any network fetch. `federation/http.ts` `signedProviderFetch` makes provider-signed outgoing calls. Remote real-time is **direct-WS** (§8.5): a remote member connects straight to the channel's home provider. The injectable `federationFetch` (via `createApp` deps) is how the server-level two-provider tests (`packages/server/test/helpers/two-provider.ts`) and the e2e harness route loopback peers.

## Testing & conformance
- **Conformance is automated:** `packages/shared/test/conformance.test.ts` (golden vectors) + `packages/server/test/conformance.test.ts` (live responses validated against the actual `../ofscp/schemas/v0.1` JSON Schemas via ajv) + `packages/server/test/checklist.test.ts` (the §12 coverage map). The map is data in `packages/server/test/checklist/` — one module per area (`auth-signing`, `groups-messages`, `media-users`, `realtime-federation`, `provider-optional`, `client`); each entry is the verbatim §12 `item`, its `level`, the `covers` test files, a `status` (`covered`/`partial`/`missing`) and a `note` (required unless covered). The test parses §12 from `../ofscp/docs/ofscp_spec.md` and fails unless each level's items match exactly, every mapped file exists, and `CONFORMANCE.md` (generated, never hand-edited) matches the render — after changing the map run `bun run conformance:render`.
- **Playwright:** `e2e/harness/` exposes `bootServer(extraEnv)` and `startTwoProviders()`; `harness/auth.ts` `registerUser(page, baseURL, handle)`. Browser channel: bundled Chromium doesn't support this dev OS, so it uses system Chrome via `channel` — override with `PW_CHANNEL=chromium` (CI installs it); `PW_WORKERS` caps parallelism.
